# Before-vs-After RAGAS Report — W7 D3

The four RAG 2.0 upgrades (hybrid retrieval via RRF, MMR diversification, cross-encoder
reranking, JSONB metadata pre-filtering) measured against the W7 D2 single-cosine baseline,
each in isolation and all together.

Regenerate with:

```bash
cd taxcalc-ai
# Two columns: baseline and all-four-on.
uv run python -m taxcalc_ai.eval.run_ragas --all-on
# Six columns: baseline, each flag alone, all-on. This is what attributes a delta to a stage.
uv run python -m taxcalc_ai.eval.run_ragas --matrix
# A cheap smoke run; judging cost is linear in rows x metrics x configurations.
uv run python -m taxcalc_ai.eval.run_ragas --matrix --limit 5
```

Required in the environment: `TAXCALC_AI_PG_DSN` (a corpus seeded for `tenant-a`),
`TAXCALC_AI_REDIS_URL`, and `ANTHROPIC_API_KEY` (or `TAXCALC_AI_ANTHROPIC_API_KEY`) for both
the generator and the RAGAS judge.

## Status of this report: NOT MEASURED

**Every cell below reads `n/m` — not measured — and that is the literal truth, not a formatting
placeholder.** The harness runs, the report renders, and the numbers are absent.

Two different reasons, in the two different places this is run:

* **Locally**, no evaluator credential exists at all: `TAXCALC_AI_ANTHROPIC_API_KEY` is unset
  and `.env` does not exist, so `tests/test_ragas_gate.py` skips on the `skipif` decorator
  before any judging is attempted.
* **In CI**, the credential *does* exist — `secrets.TAXCALC_AI_ANTHROPIC_API_KEY` is configured
  and reaches the step — and the run still measures nothing, because the Anthropic workspace is
  **spend-capped**. This is the exact failure W7 D2 wrote the NaN handling for: RAGAS's executor
  catches each judging job's exception itself, logs it at ERROR, and writes NaN into that row's
  score, so a capped evaluator does not raise. It returns a complete result whose every value is
  NaN. Observed on PR #60, run
  [35096240840](https://github.com/AI-Native-2026-07-29-Intuit/arush-adabala-tax-liability/actions/runs/35096240840),
  where both RAGAS steps reported:

  > `evaluator unavailable (every metric returned NaN; RAGAS logged per-job errors at ERROR
  > level). This run evaluated NOTHING — the golden set and the floors are unchanged and
  > untested.`

The second reason is the one worth internalising: a configured secret is not a working
evaluator, and the difference between them is invisible unless something is specifically
looking for it. **Fix:** raise the workspace spend limit in the Anthropic console
(Settings → Limits), then re-run the gate and regenerate this report.

This follows the W7 D2 discipline recorded in `PYTHON.md` under *"A skipped gate must not read
as a gate that passed"*. Writing plausible numbers into this table would make an unmeasured
pipeline indistinguishable from a measured one — and this table is precisely the artefact a
later day would consult to decide whether the reranker is worth its latency. A fabricated
`+0.13` on `context_precision` is not a harmless placeholder; it is a decision input that is
wrong, in a document whose whole purpose is to be trusted.

`n/m` is also what the renderer emits for any configuration absent from its input, by design:
a column that was not run must not render as a column that scored badly, and must not silently
vanish from the report.

What is verified without an evaluator: the pipeline runs end to end under every flag
combination, each stage's behaviour is pinned by its own tests
(`tests/test_hybrid_rrf.py`, `tests/test_rerank.py`, `tests/test_semantic_cache.py`,
`tests/test_tenant_isolation.py`), and `tests/test_ragas_gate.py::`
`test_the_gate_threshold_is_stricter_than_the_w7d2_floor` passes without credentials — so the
0.85 gate cannot be quietly lowered even while it cannot be measured.

## Cells below 0.85

**The authoritative list is the one generated inside the markers above** — `render_report`
appends ` :warning:` to every measured cell below 0.85 and rolls them up beneath the tables,
marking the `faithfulness` rows as the ones that gate the build. That is deliberately not a
hand-maintained list: a flag written by hand is lost the first time anyone regenerates the
report, which is the same class of error as the generator overwriting the prose.

**As of this commit that list reads "not determinable", because none of the 24 score cells
holds a measurement** (nor do the 20 delta cells). Under the CI gate's own rule —
`faithfulness < 0.85` is fatal — the `faithfulness` row is the one that blocks, and it is
unmeasured rather than passing: `tests/test_ragas_gate.py` reports this as a **skip**, and
`tests/conftest.py` re-emits every skip as a GitHub Actions `::warning::` annotation plus a
job-summary line, so a reviewer looking at the checks list sees "this check did not run" rather
than a green tick.

An unmeasured cell is not a failing cell, and the roll-up says so in those words rather than
listing all 24 as sub-0.85 — "we did not measure this" and "this scored 0.31" are different
facts, and a report that conflates them argues for ripping out a stage that may be fine.

## What each column would attribute, and why the matrix has six of them

Attribution is the reason this is a matrix and not a before/after pair. Turning all four flags
on and observing that faithfulness rose tells you the bundle helped; it does not tell you that
all four helped. One stage may be neutral, and one may be actively negative and masked by the
others. Each column isolates one flag so the next person can *remove* the stage that is paying
latency for nothing — which is the decision this document exists to support.

What each stage can move, mechanically:

* **hybrid** (`RAG_USE_HYBRID`) — should move `context_recall` most. It adds a second retriever
  whose failure modes are the inverse of the dense path's: exact terms, form numbers and
  statutory phrases that cosine similarity buries. Documents only the sparse path finds are
  recall the baseline could not reach at any `k`.
* **rerank** (`RAG_USE_RERANK`) — should move `context_precision` and, through it,
  `faithfulness`. The cross-encoder is the only stage that reads the query and the passage in
  the same forward pass, so it is the only one that can distinguish "about the same topic" from
  "answers this question". Precision improvements propagate to faithfulness because a generator
  given less irrelevant context has less to be unfaithful about.
* **mmr** (`RAG_USE_MMR`) — should move `answer_relevancy` on multi-aspect questions and barely
  touch `context_precision`. It removes redundancy, not irrelevance: replacing four
  restatements of one fact with four different facts gives a multi-part question something to
  answer, while each individual chunk was already on-topic.
* **filter** (`RAG_USE_FILTER`) — should move little on this eval set and is load-bearing
  anyway. The golden set is single-jurisdiction, so a jurisdiction pre-filter has almost nothing
  to exclude. It exists for compliance: it is what stops a California question being answered
  from a New York chunk, which is a correctness property the aggregate cannot see and a metric
  delta near zero does not argue against.

These are the mechanisms, stated as expectations to be tested — **not** results. The
`n/m` cells above are what this branch actually knows.
